# 事故复盘

> 读者：工程团队、面试官。
> 本文给出一个**可直接复制填写**的复盘模板、严重度分级，以及一个已填案例（E8a 的 SSE 续期静默失效）。
>
> 复盘的目的不是追责，而是把「这次为什么没被更早发现」变成下一次的检查项。所有复盘默认 **blameless**：只讨论系统与流程，不讨论个人。

## 1. 什么时候写复盘

| 严重度 | 定义 | 是否写复盘 |
|---|---|---|
| **S1** | 数据 / 资金 / 安全受损 | 必须，24 小时内出初稿 |
| **S2** | 核心链路不可用（登录、对话、回测、模拟盘、研报） | 必须，48 小时内出初稿 |
| **S3** | 局部功能降级、静默失效、可绕过 | 建议写；同类问题第二次出现必须写 |
| **S4** | 文档 / 流程 / 工具链问题 | 可选；影响交付节奏时写 |

**与故障演练的区别**：`scripts/drill_reliability.py` 的演练报告是**预设故障、断言通过**；复盘是**真实发生、根因未知**。两者并列成可靠性证据，但不混称。

## 2. 复盘模板

> 复制下面整段到新文件，按实际情况填写。删掉不适用的行，不要留空标题。

```markdown

| 负责人 | <角色> |
| 评审人 | <角色> |

## 一句话摘要

<两句话内说清：什么坏了、影响了谁、现在什么状态。>

## 影响面

- **用户/数据**：<哪些用户、哪些数据、是否可恢复>
- **安全/合规**：<是否涉及密钥、越权、注入、审计缺口>
- **持续时间**：<从首次发生到恢复的墙钟时间>

## 根因（5 Whys）

1. 为什么会出现这个现象？→ <直接原因>

3. 为什么没有被更早发现？→ <检测缺口>
4. 为什么检测缺口存在？→ <流程/设计缺口>

**根因一句话**：<可复述、可验证的陈述。>

## 处置与恢复

- **止血**：<先做了什么让影响停止扩大>
- **修复**：<代码 / 配置 / 数据修复，附 commit>
- **验证**：<用什么断言/命令证明恢复>
- **回滚**：<是否需要、如何回滚>

## 复发预防

| 行动项 | 类型 | 负责人 | 截止 | 状态 |
|---|---|---|---|---|
| <加守卫用例 / 加告警 / 改流程 / 改文档> | 检测 / 预防 / 缓解 | <角色> | YYYY-MM-DD | 待办 / 完成 |

## 证据

- <日志路径 / 指标截图 / 请求 id / commit / 用例名>
- **不要**把密钥、token、用户隐私放进复盘。

## 经验教训

- **做对了什么**：<值得保留的做法>
- **做错了什么**：<流程/设计上的问题，不写个人>
- **下次怎么更早发现**：<具体检查项>
```

## 3. 已填案例：SSE 续期静默失效

### 元信息

| 项 | 值 |
|---|---|
| 编号 | INC-20261015-01 |
| 日期 | 2026-10-15 |
| 严重度 | **S3**（静默失效；若未在交付前发现，活跃用户会在 7 天后被登出，且无任何报错） |
| 状态 | 已关闭 |
| 发现方式 | E8a 安全加固的代码审查 |
| 负责人 | 后端 |
| 评审人 | 安全 / 后端 |

### 一句话摘要

会话滑动续期的 `Set-Cookie` 挂在 `require_user` 依赖注入的 `Response` 上，在 chat / research / tasks-events 三条 **SSE 路由**上静默不生效——响应照常 200、帧照常发，只是没有续期 cookie。

### 影响面

- **用户/数据**：活跃使用 SSE 的用户不会续期，7 天 TTL 到期后被登出；无数据损坏
- **安全/合规**：不涉及密钥泄露或越权；但「活跃即续」的会话策略在三条核心路径上失效
- **持续时间**：若未发现，会持续到用户被登出；本次在交付前拦截
- **影响半径（blast radius）**：三条 SSE 路由（chat / research / tasks-events），JSON 端点不受影响

### 时间线

| 阶段 | 事件 | 证据 |
|---|---|---|
| E8a 审查 | 检查「续期是否覆盖所有端点」时，注意到三条 SSE 路由直出 `StreamingResponse` | `api/chat.py`、`api/research.py`、`api/tasks.py` |
| 同日 | 复现：SSE 响应 200、帧正常，响应头无 `Set-Cookie` | 手工请求 + 响应头抓取 |
| 同日 | 根因确认：FastAPI 在「端点直出 `Response`」路径上不合并注入 `Response` 的头 | `fastapi/routing.py` 的 `isinstance(raw_response, Response)` 分支 |
| 同日 | 修复：续期改为纯 ASGI 中间件，与端点形态无关 | `core/session.py::SessionRenewalMiddleware` |
| 同日 | 守卫：跑真 SSE 路由的用例 | `test_renewal_also_lands_on_sse_routes` |

### 根因（5 Whys）

1. **为什么没有续期 cookie？** → 续期逻辑写在 `require_user` 依赖里，通过注入的 `Response.set_cookie` 签发。
2. **为什么依赖里的 `Response` 在 SSE 路由上不生效？** → FastAPI 对「端点直接返回 `Response`（含 `StreamingResponse`）」的路径只带走 `background`，**不合并**注入 `Response` 的头。
3. **为什么没有更早发现？** → JSON 端点上一切正常；SSE 路由的测试只断言了状态码与帧，没有断言响应头。
4. **为什么测试没有断言响应头？** → 续期是横切关注点，原测试按「端点功能」组织，没有按「横切面 × 端点形态」组织。
5. **为什么设计允许这个缺口？** → 把「响应头层面的东西」挂在了依赖上；依赖只在「不直出 `Response`」的端点生效，而这条例外是静默的。

**根因一句话**：**响应头层面的横切逻辑不能挂在依赖注入上**——只要有一个端点直出 `Response`，它就在那条路上静默失效。

### 处置与恢复

- **止血**：无需止血（未上线）
- **修复**：`core/session.py` 改为纯 ASGI 中间件；与端点形态无关；只在成功响应（<400）上续；只给通过 `require_user` 的请求续；响应已有 `Set-Cookie` 时不续（登出必须能真正清掉 cookie）
- **验证**：`test_renewal_also_lands_on_sse_routes` 跑真 SSE 路由 `GET /api/v1/tasks/{id}/events`，断言响应头有续期 cookie；全量离线与 ruff 通过
- **回滚**：不需要

### 复发预防

| 行动项 | 类型 | 负责人 | 截止 | 状态 |
|---|---|---|---|---|
| 续期改中间件，附真 SSE 路由用例 | 预防 | 后端 | 2026-10-15 | 完成 |
| 安全响应头同样走中间件（不挂依赖） | 预防 | 后端 | 2026-10-15 | 完成 |
| 新增横切逻辑时，检查「是否直出 `Response`」 | 流程 | 后端 | 持续 | 完成 |
| 复盘模板与评审清单收录本条判据 | 流程 | 工程 | 2026-10-20 | 完成 |

### 证据

- `backend/app/core/session.py::SessionRenewalMiddleware`
- `backend/tests/test_session_renewal.py::test_renewal_also_lands_on_sse_routes`
- [P3 SPEC §8.3](../specs/P3-En.md)

### 经验教训

- **做对了什么**：在交付前用「横切面 × 端点形态」的视角审查，而不是只跑一遍 happy path。
- **做错了什么**：把响应头逻辑挂在依赖上；SSE 测试只断言帧、不断言头。
- **下次怎么更早发现**：凡是「响应头 / cookie / 中间件」相关改动，必须有一条**直出 `Response` 的端点**用例；凡是横切逻辑，先问「它在哪种端点形态下不生效」。

## 4. 复盘检查清单

写完复盘后逐条自查：

- [ ] 时间线能对上证据（日志 / 指标 / commit），没有「大约」
- [ ] 根因是**一句话**，不是「多个原因共同导致」
- [ ] 每个行动项有类型、负责人、截止，且能验证
- [ ] 区分了「检测缺口」与「修复缺口」——两者都要有行动项
- [ ] 没有把密钥、token、用户隐私写进复盘
- [ ] 没有把「演练通过」当成「事故不会发生」
- [ ] 复盘结论已同步到相关 SPEC / 评审清单 / 测试
