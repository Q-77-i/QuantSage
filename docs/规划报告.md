## 一、先说结论：这个项目的差异化在哪

调研了一个残酷的事实：**`TauricResearch/TradingAgents` 有 10.5 万 star，定义了多 Agent 投研的标准角色划分，但它至今零 RAG、零向量库、无 Web UI。** 而金融新闻 RAG 方向全球最高星的开源项目只有 1,057 star，中文 A 股方向几乎没有成熟实现。

同时，**"MCP + 金融新闻 RAG + 回测"三者打通的项目，目前不存在。**

这不是让你去蹭热度，而是说：**你的选题踩在一个真实的空白上**。而更关键的是——你手上的数据源给了你一个别人拿不到的东西。

### 你的护城河：`available_at`

小石平台的 PIT 语义写得极其严谨：

```
event_time   事发时间
available_at 平台首次可使用时间   ← 回测只能看到这个时间点之前的信息
observed_at  观察时间
```

并且平台明确承诺**"不把当前最终值倒灌到过去"**。

这让「知策」能做一件市面上 99% 的"LLM+量化"项目做不到的事：**回测到第 T 天时，Agent 只能检索到 `available_at <= T` 的新闻。** 绝大多数同类项目在用抓取时间戳或无过滤地检索全量语料——它们在无意识地穿越未来，回测结果全部虚高，而且是**面试官最容易一眼看穿的硬伤**。

RAG 调研把这条列为"最容易被忽略、但决定成败的第一原则"。**你的数据源天生满足它。**

### 因此项目的一句话定位

> **知策 QuantSage —— 一个前视偏差为零的 AI 投研 Agent：多 Agent 并行取证、PIT 约束的语义检索、结论可回测验证。**

三个关键词各有对应：**PIT 检索**（RAG）、**多 Agent 取证**（LangGraph）、**可回测验证**（量化）。面试时这句话讲完，你就赢了 90% 的同类项目。

## 二、技术栈选型（对比 + 理由）

### 2.1 编排框架：为什么是 LangGraph + LangChain 而不是别的

| 框架          | Star  | 活跃度         | 判断                                                  |
| ------------- | ----- | -------------- | ----------------------------------------------------- |
| **LangGraph** | 41.6k | 🟢 极活跃       | ✅ **选用**                                            |
| CrewAI        | 58.5k | 🟢              | ❌ 状态无持久化 store，复杂分支弱，适合原型不适合生产  |
| AutoGen       | 61.0k | 🔴 **已维护态** | ❌ 原仓库最后 push 2026-04，微软已改推 agent-framework |
| agno          | 42.2k | 🟢              | ⚠️ 轻量好用，但金融场景需要的可审计性弱于 LangGraph    |

**选 LangGraph 的决定性理由**：它是唯一原生支持 **checkpoint + time-travel + human-in-the-loop** 的框架。金融场景要的是"确定性、可审计、可复现"——这三点恰好是 LangGraph 的设计目标，也是其他框架的短板。

**职责边界**（这条很重要，很多项目在这里打架）：

```
LangGraph StateGraph  ← 外层：控制流、循环、持久化、并行、HITL
  ├─ node: 调 LCEL 链        ← LangChain 只活在节点内部（RAG/抽取/格式化）
  ├─ node: 调子 Agent        ← subagents-as-tools
  └─ node: 纯 Python          ← 风控闸门、计算、校验（绝不让 LLM 决定合规）
```

判据只有一条：**控制流里有没有"往回指的箭头"**。有循环/反思/重试路由 → LangGraph；单向 DAG → LCEL 就够。RAG 检索链、摘要、结构化抽取都是单向的，全部做成节点内的 LCEL。

**⚠️ 一个必须避开的坑**：`langgraph-supervisor` 已停止维护（2025-11 后无更新），官方迁移指南指向 **subagents-as-tools**。网上 2024–2025 年的教程清一色还在教 supervisor，照着写就是过时代码。

### 2.2 前端

| 方案                                                         | 判断                                           |
| ------------------------------------------------------------ | ---------------------------------------------- |
| **Next.js 15 (App Router) + TypeScript + Tailwind + shadcn/ui** | ✅ **选用**                                     |
| Vite + React SPA                                             | 更简单，但没有 SSR，研报页无法被分享/索引      |
| Vue 3 + Nuxt                                                 | 国内生态好，但 AI 应用前端范例少，面试辨识度低 |

选 Next.js 的理由：**研报需要可分享的独立 URL**（这是产品化的关键一步，也是你的演示素材），App Router 的 Server Component 天然适合；同时中大厂对 Next.js + TS 的认可度最高。

**图表**：`TradingView Lightweight Charts`（K 线，金融专用，体积仅 45KB）+ `ECharts`（净值曲线、因子分析、热力图）。这个组合是国内量化前端的实际标配。

### 2.3 后端与数据

| 层        | 选型                                | 理由                                                         |
| --------- | ----------------------------------- | ------------------------------------------------------------ |
| Web       | **FastAPI + Pydantic v2 + Uvicorn** | 量化生态全在 Python，没有第二选择                            |
| 历史行情  | **Parquet + DuckDB**                | 5859 个 Parquet 分片**直接用 SQL 查，零 ETL**。日线全市场 1M 行/年，DuckDB 秒级响应 |
| 业务数据  | **PostgreSQL 18**（已在跑）1        | 顺带承担 LangGraph checkpointer                              |
| 缓存/限流 | **Redis**（已装）                   | 分布式令牌桶、会话、Single-flight                            |
| 向量库    | 见下方决策                          |                                                              |

**DuckDB 这一条值得单独说**：调研里所有项目都在费劲把行情导进数据库，而你的数据源已经给了按年/按标的切好的 Parquet。DuckDB 直读 Parquet 意味着**整个数据同步层可以不存在**——少一个组件、少一类 bug、少一个运维负担。这是"由简到繁"的典范。

### 2.4 模型：双档策略（已验证）

⚠️ 实测确认：`deepseek-chat` / `deepseek-reasoner` **已下线**，当前可用的是：

| 模型              | 用途                                   | 依据                                         |
| ----------------- | -------------------------------------- | -------------------------------------------- |
| `deepseek-v4-pro` | 深度推理：辩论、综合撰写、组合决策     | TradingAgents 验证过的 `deep_think_llm` 策略 |
| `deepseek-flash`  | 快档：工具调用、摘要、意图路由、格式化 | `quick_think_llm`                            |

**双档策略是成本控制的核心手段**——分析师/路由用快档，只有需要真正推理的节点用深度档。这在简历上是可以量化讲成本的加分项。

## 三、系统架构

```
┌─ 前端 Next.js 15 ──────────────────────────────────────┐
│  对话界面(SSE流式) │ 研报页(可分享URL) │ K线+净值回测视图  │
└────────────────────────┬───────────────────────────────┘
                         │ SSE / REST
┌─ 网关层 ────────────────▼───────────────────────────────┐
│  request_id → JWT鉴权 → 限流(Redis令牌桶) → 输入校验        │
└────────────────────────┬───────────────────────────────┘
┌─ 编排层 LangGraph ──────▼───────────────────────────────┐
│  意图路由 ──┬── 快路径: RAG链 → 生成          (80%查询)   │
│            └── 深路径: 并行取证 → 辩论 → 综合 → 风控闸门   │
│  Checkpointer(Postgres) │ Store(跨会话记忆) │ interrupt()  │
└────────────────────────┬───────────────────────────────┘
┌─ 能力层 ────────────────▼───────────────────────────────┐
│ 小石MCP(行情/新闻/事件) │ RAG检索 │ 回测引擎 │ 因子计算     │
└────────────────────────┬───────────────────────────────┘
┌─ 数据层 ────────────────▼───────────────────────────────┐
│ Parquet+DuckDB │ Postgres │ Redis │ Qdrant │ Langfuse     │
└─────────────────────────────────────────────────────────┘
```

### Agent 系统应该包含哪些模块

这是你问的重点，我按"一个完整 Agent 系统的必备模块"来拆：

| #    | 模块         | 职责                       | 我们的实现                           |
| ---- | ------------ | -------------------------- | ------------------------------------ |
| 1    | **接入层**   | 鉴权、限流、请求校验       | FastAPI 中间件 + Redis 令牌桶        |
| 2    | **会话层**   | thread 管理、状态恢复      | LangGraph Checkpointer (Postgres)    |
| 3    | **编排层**   | 图流转、并行、循环、中断   | LangGraph StateGraph                 |
| 4    | **能力层**   | 工具注册、执行、审计       | 原生 function calling + 小石 MCP     |
| 5    | **记忆层**   | 短期/长期/语义/程序性      | Checkpointer + Store + Qdrant + 文档 |
| 6    | **模型层**   | 路由、降级、熔断、成本核算 | 双档 DeepSeek + LiteLLM 网关         |
| 7    | **可观测层** | trace、指标、成本归因      | Langfuse 自托管 + OTel GenAI span    |
| 8    | **可靠性层** | 重试、超时、熔断、幂等     | 分层策略 L0–L7                       |
| 9    | **评估层**   | 检索质量 + 生成质量        | RAGAS + 自建集 + DeepEval CI         |
| 10   | **安全层**   | 注入防护、沙箱、审计       | 工具白名单 + 代码沙箱                |

多数学生项目只有 1/3/4 三层。**能把这 10 层讲清楚，本身就是面试的差异化。**

### 一次 Agent 请求的完整链路

```
用户输入
 ①  Nginx/TLS
 ②  FastAPI 中间件：request_id、结构化日志
 ③  JWT 鉴权
 ④  Redis 令牌桶限流（按 user+endpoint）
 ⑤  输入校验 + 注入检测
 ⑥  会话加载：thread_id → Postgres 恢复 state
 ⑦  意图路由：简单问答 → 快路径(RAG)；复杂研究 → 深路径(LangGraph)
 ⑧  编排执行：LangGraph 图流转 ⇄ 工具调用 ⇄ RAG 检索
 ⑨  模型调用：路由到 flash/pro，带重试→降级→熔断
 ⑩  SSE 流式输出：逐字 + 中间步骤可视化
 ⑪  落库：checkpoint + 决策日志 + trace
 ⑫  可观测：OTel span → Langfuse
```

**第 ⑦ 步值得强调**：调研数据表明，简单查询走 RAG 直通（1 次 LLM 调用、~1.4s、$0.0021），复杂查询才进多 Agent（3.6 次调用、~4.9s、$0.0078）。**常开多 Agent 循环是 3.7 倍成本和 3.5 倍延迟**，而在简单问题上是零质量增益。路由本身就是个技术亮点。

## 四、Multi-Agent 设计

### 拓扑：确定性外壳 + 并行取证 + 有上限辩论 + 代码化风控

```
START → 意图路由
         │
    ┌────┴──── 深路径 ────────────────────────┐
    │                                          │
    │  ┌── 并行取证 (fan-out) ──┐               │
    │  │ 行情技术面 │ 新闻事件(RAG,PIT)          │
    │  │ 基本面     │ 因子量化                  │
    │  └────────┬───────────────┘               │
    │      证据归并 (reducer)                    │
    │           │                                │
    │      Bull ⇄ Bear 辩论 (≤3轮，硬上限)        │
    │           │                                │
    │      综合撰写 (单点，不并行)                 │
    │           │                                │
    │      风控闸门 (纯代码，非 LLM)               │
    │           │                                │
    │      interrupt() 人工审批 (超限时)           │
    └───────────┬────────────────────────────────┘
              END → 落库 → 可观测
```

**四条设计纪律，每条都有调研依据：**

1. **"读"并行，"写"单点。** Anthropic 自己的 Research 系统就是这个形态——检索可以并行，**写作必须由单一 Agent 一次完成**。并行写会产生冲突决策，合并代价极高。
2. **辩论必须有轮次上限。** 实测经验：辩论阶段的 token 成本是分析阶段的 **3–5 倍**，且小模型会陷入无法收敛的循环。用 `debate_round` 计数器 + 条件边，2–3 轮后强制收敛。
3. **风控闸门用代码，不用 LLM。** LLM 只做研究与论证；仓位限制、合规检查用确定性 Python。出错可复现、可审计——这在金融场景是生命线。
4. **并行节点内部必须 try/except。** LangGraph 中同一 superstep 内任一节点抛异常，会**取消所有兄弟节点**。一个数据源超时炸掉整轮投研是不可接受的——错误要写进 `errors` 列表，让聚合节点基于部分结果继续。

### A2A：不做，但要说清为什么

A2A 已于 2026-03 发 v1.0，150+ 组织支持，还进了 Linux Foundation。但**它的适用条件是"跨异构运行时/跨组织"**。

我们是单体项目，所有 Agent 在同一个进程里。上 A2A 只会增加 HTTP 跳数和序列化开销，零收益。

**触发条件**（满足任一才需要）：① 出现第二个异构 Agent 运行时；② 要把投研能力作为服务卖给别人的 Agent；③ 跨组织 Agent 交易。

**现在要做的"零成本预留"**：把每个 Agent 的能力描述、输入/输出 schema 抽成一份内部元数据（等价于 Agent Card），服务边界走 HTTP 而非进程内直调。将来只需加一层 binding。

> 面试时可以这样答：「A2A 解决的是跨组织 Agent 互操作，我们单体架构下引入它只有开销没有收益。但我把 Agent 能力元数据抽出来了，将来要对外开放时加一层 binding 就行。」——**能说清"为什么不做"比盲目上更显判断力。**

### MCP：消费 + 对外暴露

| 方向                          | 做不做                    | 理由                                                         |
| ----------------------------- | ------------------------- | ------------------------------------------------------------ |
| **消费**小石 MCP              | ✅ 必须                    | 数据源官方提供本地 stdio MCP Server                          |
| **内部工具**（RAG/回测/因子） | ❌ 用原生 function calling | MCP 有 20–60ms 额外开销；内部调用不需要协议层                |
| **对外暴露**自己的 MCP Server | ✅ 加分项                  | 把"财经新闻 PIT 检索"包成 MCP，Claude Desktop / Cursor 可直接调用 |

第三条是**2026 年校招辨识度最高的技术标签**——调研结论是"MCP + 金融新闻 RAG + 回测三者打通的项目目前不存在"。工作量不大（FastMCP 一个文件），但叙事价值极高。

⚠️ **安全红线**：MCP 的 tool description 和返回值**都是注入面**。基准测试中 o1-mini 的中招率 72.8%，DeepSeek-R1 70.9%。任何进入决策的数据都要有来源标注和可验证链路。我们的数据源恰好提供了 `source_verified` 字段——**把它做进 UI**。

### Harness：你已经在用了，但要补三个缺口

Harness = 模型之外的那层壳：上下文组装、工具执行、循环控制、状态管理。**LangGraph 就是我们的 Harness**，不需要再造一个。

但 LangGraph 有三个缺口需要自研补齐：

1. **工具执行器** — 带重试/超时/审计/幂等的统一执行层
2. **上下文预算管理器** — 步数、token、时间、成本的硬上限（防失控）
3. **代码执行沙箱** — 如果让 Agent 写因子代码，必须限制在子进程 + 资源配额里

> 调研还发现 LangGraph 开源版**不含**：故障自动检测、崩溃后 workflow 自动恢复、防重复处理同一 thread_id 的分布式锁、Agent 身份与安全。这些在简历上写"我知道它缺什么并且自己补了"，比写"我会用 LangGraph"强一个量级。

### Memory：两套系统，都要做

你提到的「CLAUDE.md → AutoMemory → 项目级文档」和产品的运行时记忆**是两套完全不同的东西**，恰好对应同一个设计哲学：

|        | **设计期记忆**（我们协作开发用）   | **运行期记忆**（产品用）      |
| ------ | ---------------------------------- | ----------------------------- |
| 载体   | `CLAUDE.md` → AutoMemory → `docs/` | Checkpointer → Store → Qdrant |
| 性质   | 静态、人写、进 Git、可 review      | 动态、Agent 写、进数据库      |
| 作用域 | 整个仓库                           | 用户 / 会话 / 实体            |
| 类比   | 程序性记忆（本能）                 | 语义+情节记忆（见闻）         |

**产品侧三层**：

- **Checkpointer**（Postgres）— thread 内短期状态，支持 time-travel 与中断恢复
- **Store**（Postgres）— 跨 thread 长期记忆：用户偏好、标的画像、历史决策日志
- **Qdrant** — 语义记忆（新闻语料，只读、共享）

> **一条铁律**：合规与风控规则**绝不让 LLM 动态改写**。procedural memory 自更新在金融场景是高危反模式——规则只能进 Git，走 PR 审查。

## 五、RAG 设计（你问的五个决策）

### 决策 1：语料怎么获取 —— 这是最需要你注意的一条

**现实约束**：在线事件接口**单次最多 92 天**（平台明确保护）。但错误信息透露了更早历史可以通过**事件归档目录 + R2 下载**获取（归档入口在 CLI/MCP 目录下，安装后才能确认）。

**实测数据量**：最近 24 小时 **1,235 条**事件（news 1160 / announcement 69 / person 6）。按此估算：

| 来源               | 规模                       |
| ------------------ | -------------------------- |
| 在线 92 天窗口     | ≈ **11.4 万条**            |
| 归档回溯（待确认） | 待定                       |
| 日增量 ETL         | ≈ 1,235 条/天 ≈ 45 万条/年 |

**所以语料策略是**：

1. **立即启动日增量 ETL** —— 语料库是时间的函数，**从项目第一天就要开始积累**，晚一天就少一天
2. **跑一次 92 天全量回填** —— 立即可用的基线语料
3. **用归档目录做长历史回填** —— 待确认可用性

这是一个真实的**增量数据管道工程**，本身就是简历内容（调研里 FinGPT 的数据工程层被列为"最容易做扎实也最容易讲出故事的部分"）。

**每条记录的结构**（实测）已经非常丰富，几乎不需要额外加工：

```json
{
  "event_id": "news:2234020",
  "title": "...", "summary": "...",
  "event_time": "2026-09-14T16:31:25+08:00",
  "available_at": "2026-09-14T08:32:23+00:00",   ← PIT 约束的核心字段
  "content_hash": "c63d8cd9...", "is_corrected": false,
  "direction": "中性", "confidence": 0.4,
  "industries": [], "stocks": [], "person": [],
  "factor_scores": { "score": 42.539, "inputs": {10个维度}, "version": "factor-v2" }
}
```

注意 `factor_scores` 里有 10 个预计算维度（urgency / freshness / market_impact / source_credibility…）——**这些直接就是元数据过滤和排序的现成特征**。

### 决策 2：分块策略 —— 反直觉的结论

**不要做递归切分。** 实测发现 `content_level` 是 `headline_only` 或 `derived_summary_or_excerpt`——即**标题 + 摘要**，典型长度 100–300 字。

> 一段 200 字的摘要是不可切的。切了就废。

所以正确策略是 **文档级 parent + 元数据 header 拼接**（Anthropic Contextual Retrieval 的零成本版）：



```
【标题】央行宣布降准0.5个百分点，释放长期资金约1万亿元
【时间】2026-05-07  【方向】利多  【重要度】78.3
【行业】银行/地产  【标的】沪深300
【正文】中国人民银行决定于2026年5月15日下调金融机构存款准备金率...
```

官方数据显示上下文增强让检索失败率降 35%。而**财经新闻「标题即主题」——元数据拼接已经吃掉了大部分收益，且不花一分钱 LLM 调用、不花额外存储，BM25/稀疏分支同样受益**。

对少数长文本（公告、研报）才走递归分块 + 父子文档（small-to-big）。

### 决策 3：Embedding —— BGE-M3

| 模型                 | 维度 | 最大输入  | 稀疏                | Mac 内存 |
| -------------------- | ---- | --------- | ------------------- | -------- |
| **BGE-M3** ✅         | 1024 | 8192      | ✅ 稠密+稀疏+ColBERT | ~5GB     |
| Qwen3-Embedding-0.6B | 1024 | 32768     | ❌                   | ~1.1GB   |
| bge-large-zh-v1.5    | 1024 | **512** ⚠️ | ❌                   | 轻       |

**选 BGE-M3 的决定性理由**：它**一次前向同时输出稠密向量 + 稀疏向量**。

这为什么关键？稠密嵌入对股票代码、公司简称（"中行"、"茅子"）、指标名（"社融"、"LPR"、"MLF"）这类字符串**天然不敏感**——实测中稠密模型在"主客体互换"硬负例上几乎全错。而财经文本恰恰实体密集。

BGE-M3 免费送稀疏向量 → **你不需要维护独立的 BM25 索引、不需要 jieba 分词、不需要自定义词典**。三个最容易出 bug 的地方全省了。对单人项目这是巨大的工程量节省。

### 决策 4：Reranker —— 要上，选编码器架构

| 模型                           | 参数 | 架构       | 中文 CMTEB-R | Mac 速度       |
| ------------------------------ | ---- | ---------- | ------------ | -------------- |
| **bge-reranker-v2-m3** ✅       | 0.6B | **编码器** | **72.16**    | 快             |
| Qwen3-Reranker-0.6B            | 0.6B | 解码器     | 71.31        | **慢 3–10 倍** |
| gte-multilingual-reranker-base | 0.3B | 编码器     | **74.08**    | 更快           |

**两个反直觉发现**：① 纯中文检索上，bge-reranker-v2-m3 **反超** Qwen3-Reranker-0.6B（Qwen 自己的表里就写着）；② Qwen3-Reranker 是**解码器**架构，同参数量下 CPU 上慢 3–10 倍——**在无 GPU 的 Mac 上这是致命的**。

> 编码器 vs 解码器的选择，在 Mac 上的重要性**高于榜单分数**。

收益：召回 20 篇直接塞给 LLM 准确率约 62%，**经 rerank 保留 top-3~5 可达约 89%**。

### 决策 5：向量库 —— 这里两份调研给出了不同答案，我说我的判断

|            | Qdrant                                | pgvector              |
| ---------- | ------------------------------------- | --------------------- |
| 混合检索   | ✅ **原生稠密+稀疏+服务端 RRF**        | ⚠️ 客户端融合，~12 QPS |
| 元数据过滤 | ✅ **最强**（payload 索引）            | ✅ 全 SQL              |
| 部署       | 单二进制 / Docker / 本地 `path=` 模式 | 复用现有 PG           |
| 实证项目   | open-news-mcp、Metadata-Aware-RAG     | FinSight-AI、FINCO    |

**我推荐 Qdrant**，理由是它**直接吃掉 BGE-M3 的稀疏向量**，一次请求完成 dense + sparse + RRF 融合：

```python
client.query_points(
    collection_name="fin_news",
    prefetch=[
        Prefetch(query=dense_vec, using="dense",  limit=100),
        Prefetch(query=sparse_vec, using="sparse", limit=100),
    ],
    query=FusionQuery(fusion=Fusion.RRF),          # 服务端 RRF，k=60
    query_filter=Filter(must=[                      # ← PIT 约束在这里
        FieldCondition(key="available_at",
                       range=DatetimeRange(lte=as_of)),
        FieldCondition(key="industries", match=MatchAny(any=["XS_SEMICIRCUITOR"])),
    ]),
    limit=10,
)
```

**这段代码就是整个项目的技术核心**——`available_at <= as_of` 这一行，就是"前视偏差为零"的实现。

而 pgvector 的混合检索是客户端融合，需要自己实现 BM25 + jieba + RRF，且只有 12 QPS。

**但我要诚实说明代价**：Qdrant 是多一个要运维的组件。如果你更在意"少一个服务"，pgvector 完全可行（FinSight-AI 这个最完整的 A 股 RAG 项目就是这么做的），代价是混合检索要自己写。**这是个真实取舍，我把选择权给你。**

### 完整检索管线

```
Query
 → 元数据硬过滤 [available_at ≤ as_of / 行业 / 标的 / 重要度]   ← 消除 95% 无关块
 → 并行 [稠密 top-100] ∥ [稀疏 top-100]
 → RRF 融合 (k=60)
 → bge-reranker-v2-m3 精排
 → top-3~5 送 LLM（small-to-big 取回完整父文档）
```

**实体锚点硬过滤比任何模型升级都值钱**——把搜索空间从千万块缩到千块，实测幻觉率降 70%+。

### 评估

| 层次     | 工具                                             | 验收                      |
| -------- | ------------------------------------------------ | ------------------------- |
| 检索质量 | **自建 200 条中文财经 query 集** + `pytrec_eval` | NDCG@10 / MRR / Recall@20 |
| 生成质量 | RAGAS（judge 必须用中文强模型）                  | faithfulness ≥ 0.7        |
| 回归防护 | DeepEval 写 pytest 断言进 CI                     | 调参调坏立即红灯          |

⚠️ RAGAS 在中文金融长文本上**会误判**（有实测指出 Context Recall 误判率 37%），所以自建评测集是必须的兜底。评测集的 query 要覆盖五类：事实型 / 事件型 / **数值型** / 时间型 / 多跳型。

**GraphRAG 不做**——有明确证据：FinNLP 2025 论文显示朴素 RAG 在金融叙事摘要上**全面优于** GraphRAG；且财经新闻是流不是库，实体图维护成本线性增长。用轻量实体表拿到 80% 收益，成本是 GraphRAG 的 5%。

**Agentic RAG 只做"自适应路由 + 一轮纠错"**，`MAX_ITERATIONS=3` 是甜点。常开循环在简单问题上是零增益。

## 六、可靠性与可观测性

### 分层容错（L0–L7）

| 层        | 目标             | 手段                                                        |
| --------- | ---------------- | ----------------------------------------------------------- |
| L0 入口   | 不被刷           | Redis 令牌桶（按 user+endpoint）                            |
| L1 网关   | 多供应商、预算   | LiteLLM：配额、fallback、429/5xx failover                   |
| L2 图节点 | 瞬时故障自愈     | LangGraph `RetryPolicy` + `TimeoutPolicy` + `error_handler` |
| L3 模型   | 供应商故障       | DeepSeek pro ⇄ flash 降级链                                 |
| L4 依赖   | 停止捶打故障依赖 | 熔断器（多 worker 用 Redis 共享状态）                       |
| L5 降级   | 有损但可用       | 缓存结果 / 部分结果 / **明确告知降级**                      |
| L6 护栏   | 防失控           | 步数上限、token 上限、`recursion_limit`                     |
| L7 幂等   | 防重复副作用     | 幂等键 + 结果校验                                           |

**最常见的坑**：retry 与 breaker 各自为政——熔断器已打开时重试仍在开火，超时算的是单次尝试而非含重试的总预算。**必须用统一的 policy 对象共享状态与预算。**

### 可观测性

**自托管 Langfuse**（MIT，免费自托管），产出 OTel GenAI 语义 span。

选它不选 LangSmith 的理由：① LangSmith 自托管被 Enterprise 门槛挡住；② 成本曲线——100 万事件 Langfuse ≈$101/mo vs LangSmith ≈$2,514/mo；③ 走 OTel 后端可换。

**比选型更重要的四件事**：每条 trace 记全 `模型+版本+prompt hash+工具序列+token成本+延迟+用户`；**评估进 CI 做闸门**；Agent 专属指标（工具选择准确率、**循环终止率**、p99 延迟）；前端埋点区分"用户可见延迟"与"内部推理耗时"。

### ⚠️ 一条必须处理的安全公告

2026 年披露了 **LangGraph checkpointer RCE 利用链**（三个 CVE 组合：`get_state_history()` SQL 注入 → 伪造 checkpoint → msgpack 反序列化执行）。

**加固清单**（这些是硬性要求，不是可选项）：

1. **生产必须用 Postgres checkpointer**，不能用 SQLite
2. **必须设 `LANGGRAPH_STRICT_MSGPACK=true`**
3. checkpoint 系列是**独立包**，`pip install -U langgraph` 修不全，必须逐个显式 pin 版本
4. 校验/拒绝含 SQL 元字符的 filter key
5. LangGraph server 绝不裸奔，前面必须有反向代理 + 鉴权

> 这个正好可以做成项目里的一个工程亮点：**"我在设计阶段就做了依赖安全审计"**。
